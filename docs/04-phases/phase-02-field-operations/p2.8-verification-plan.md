# P2.8 verification engine: slice plan

> [Docs index](../../README.md) › [04-phases](../README.md) › [Phase 2 plan](plan.md) · [Sub-phases](sub-phases.md#p28--verification-engine) · [Tracker](tracker.md)

**In plain words:** every shift entry gets a decision: approved, rejected, or corrected with a before-and-after
trail, and a second person for big corrections. Nobody approves their own work. Design:
[ADR-0037](../../adr/0037-verification-engine.md).

## 1. Scope

| Story | ACs in P2.8 |
|---|---|
| US-P2-VER-02 Approve | AC1 (single and bulk; bulk only for unflagged entries), AC2 (the decision bound to the hashes of every version it covers), AC3 (SoD: not own entry, not an asset the reviewer operated in that shift) |
| US-P2-VER-03 Reject | AC1 (reason code + comment; the operator sees it at the next pull, the notice is P2.10), AC2 (rejected entry kept; a resubmission is a new entry linked to it) |
| US-P2-VER-04 Correct | AC1 (meter values, fuel, shift, asset with a reason; before → after), AC2 (original `corrected`, new version linked, ledger with both hashes and the diff), AC3 (beyond thresholds: second approval by another person with `verification.items.second-approve`) |
| US-P2-VER-05 Review policies | AC1 (per record type: reviewers, auto-approval, four-eyes thresholds, SLA, escalation), AC2 (versioned, audited, pinned on each item) |
| US-P2-VER-06 SLA & escalation | AC1 (overdue items escalate and come first); AC2 digest is P2.10 |
| US-P2-FO-08 Resolve continuity exception | AC1 (reason codes), AC2 (`FRAUD_SUSPECTED` on "unexplained" or > 48 h; the executives' notice is P2.10), AC3 (reasons other than data-entry error need a second approval) |

Tests: TC-P2-VER-001 … 009 (Phase 2 plan, sub-phase card), each with a mutation check where it guards a refusal.
Done when: demo step 4 runs (a correction beyond the threshold → a second approver → the diff in the ledger).

## 3. Decisions taken here

- **Verification is its own module** with a record contract, so tickets, fuel and counts reuse it (ADR-0037 §1).
- **"Signed" is authenticated, ledgered and hash-bound** for portal decisions, as for safety-hold releases in P2.6;
  a server-signed decision document is P2.11's, if wanted (ADR-0037 §3).
- **SoD sees people, not accounts**, through an explicit office ↔ field account link set by the company
  administrator (ADR-0037 §4).
- **The controller console is P2.9**: P2.8 ships the API, the policies page and the tests; the queue screen comes next.
