# P2.5 field capture flows: slice plan

> [Docs index](../../README.md) › [04-phases](../README.md) › [Phase 2 plan](plan.md) · [Sub-phases](sub-phases.md#p25--field-capture-flows-tablet) · [Tracker](tracker.md)

**In plain words:** the operator starts and ends a shift on the tablet: finds the machine, photographs the meter,
types the value, sets the fuel level, signs, and the entry waits in the outbox until there is network. This file
splits [P2.5](sub-phases.md#p25--field-capture-flows-tablet) into small PRs, says what each one builds and how it is
tested, and records the decisions taken while planning. The server side already exists: commands
`fieldops.shift_entry.start.v1` / `.end.v1`, flags and the read API ([ADR-0034](../../adr/0034-shift-entries.md)),
envelopes ([ADR-0033](../../adr/0033-signature-envelopes-and-server-keys.md)), evidence blobs and the outbox
([ADR-0032](../../adr/0032-evidence-blobs.md)).

## 1. Scope

| Story | ACs in P2.5 | Left for later |
|---|---|---|
| US-P2-FO-01 Start a shift | AC1 (QR or list, shift preselected), AC2 (in-app photo, previous end shown), AC3 (fuel ¼ marks, remarks with the system's voice keyboard), AC4 on the tablet (below the previous end blocked; unusual jump needs a reason), AC5 capture (position in the envelope), AC6 (offline draft), AC7 (usability protocol) | AC4 meter events and AC5 geofence flag: P2.7 rules |
| US-P2-FO-04 End a shift | AC1 (from "My active shift": photo, value, fuel, stoppages), AC2 on the tablet (negative or oversized Δ blocked with the explanation), AC3 (summary start/end/Δ before signing) | the meter-event exception: P2.7 |
| US-P2-FO-05 Handover | AC1 screen (continue after the previous segment: `previousRootId`), AC2 on the tablet (no second active segment for the same operator) | |
| US-P2-FO-06 My history | AC1 for what the tablet knows (Draft, Queued, Submitted, Rejected with reason) | Approved / Corrected and AC2 re-open of a controller rejection: P2.8 (status pull of reviews) |
| From P2.2 / P2.3 | browser E2E TC-P2-SYNC-002/007/011/014; an entry signed in the browser verified end to end, also after a key rotation | |

Not in P2.5: the pre-start checklist (P2.6; demo step 1 runs without it until then), fuel issues and production
(later sub-phases), Web Push (P2.8).

## 2. Decisions taken while planning

1. **The tablet blocks what the server would only flag.** ADR-0034 stores every signed fact and flags it; US-P2-FO-01
   AC4 and US-P2-FO-04 AC2 ask the tablet to stop the operator *before* signing. Both hold: the tablet refuses to
   sign a start below the meter's previous end, a negative Δ or a Δ beyond the real length + 0.5 h, with the reason
   on screen; the server still flags whatever arrives (another tablet, an old app). The rules are the shared ones of
   slice 1 (`shiftRules.ts`), so the tablet never blocks what the server accepts unflagged.
2. **The previous end comes from a new FieldOps sync collection, `meterStates`.** The meters the tablet pulls (Assets)
   carry no value, and `assets.meters.last_value` is not written by shift entries. FieldOps owns the answer: per
   meter of the site, the last segment's end (value, time) and the open segment if any (entry id, operator, start
   value, start time, shift). The tablet's own unsent commands win over the pulled state (they are newer by
   construction), so the reference is right offline too.
3. **The shift is computed on the tablet with the server's rules, proven by a second shared vector file**
   (`tests/vectors/shift-resolution.json`): pattern versions by effective date, night shifts across midnight,
   the site's time zone (with a DST zone in the vectors even though Tunisia has none), equal times = 24 h. The server
   side runs the same file through the Organization domain. The operator can change the preselected shift only to
   the previous or the next instance (late start, early handover).
4. **Drafts live in a new Dexie table (`drafts`, schema v3)**, one per operator and form, written at every step;
   nothing of a draft is signed or sent. After an auto-lock, the draft reopens only for the same operator; another
   operator sees "a draft of <name> is open on this machine" and cannot open it (T-01). Drafts older than 24 h are
   offered for discard.
5. **The unusual-jump reason goes into `remarks`.** The record has no reason member and a new member would mean
   a new record version; the reason is prefixed in the remarks (`remarks` becomes required for that start). The
   threshold is a constant (24 h) until a company setting exists (owner input, §5).
6. **One command per signature, built by one function.** `signShiftEntry` builds the record, takes the evidence
   (meter photo, signature strokes JSON, signature PNG), computes `payloadHash`, builds the envelope (signer =
   unlocked operator, role `operator`, `context.deviceTime`, `appVersion`, `geo` when the browser gave a position
   within 10 s), signs it, and enqueues `{record, envelope, deviceSignature, captures}` with the evidence. The capture
   records ride in the signed command payload (`captures`, ADR-0032 §5); the server keeps the command as received.
7. **Position:** asked once per form with `getCurrentPosition` (high accuracy, 10 s timeout, a cached position up to
   2 min old accepted); refused or timed out → no `geo`, never a blocker. Rounded to 6 decimals as stored.
8. **Lazy chunks:** the camera (`PhotoCapture`) and the signature pad are loaded by the flows with `React.lazy` and
   preloaded when the flow opens, so the first photo does not wait on the network; the precache keeps them offline.
   The initial bundle stays ≤ 250 KB gzip (CI `bundle_budget.py`).

## 3. Slices

Each slice is one PR (`feat/p2.5-…`), tested, CI green, docs swept. Order matters: each needs the one before.

| # | Slice | Status |
|---|---|---|
| 1 | Shared validation vectors `shift-entry-rules.json` (TC-P2-FO-012) | ✅ #175 |
| 2 | In-app camera `camera.ts` / `PhotoCapture.tsx` (TC-P2-FO-002) | ✅ #176 |
| 3 | Reference for capture: `meterStates` sync collection, Dexie v3 (`meterStates`, `drafts`), shift resolution with shared vectors | ⬜ |
| 4 | Sign and enqueue: `signShiftEntry` (record, evidence, envelope, position, captures), unit and server round-trip test | ⬜ |
| 5 | Start-shift flow (UI) with drafts | ⬜ |
| 6 | "My active shift", end-shift flow and handover | ⬜ |
| 7 | "My history" (14 days) | ⬜ |
| 8 | Browser E2E (Playwright): offline start → end → sign → online; TC-P2-SYNC-002/007/011/014; envelope verified after a key rotation; 20 entries offline | ⬜ |
| 9 | Close-out: bundle budget, five languages reviewed rows, security review (T-01, T-17), usability protocol, demo steps 1–2, tracker ✅ | ⬜ |

### Slice 3: reference data for capture

- **Server (FieldOps):** `FieldOpsSync : ISyncSource` collection `meterStates`, one row per meter of the tablet's
  site: `{meterId, lastEnd: {value, at, entryId} | null, open: {entryId, operatorId, startedAt, startValue, shiftDate,
  shiftCode} | null}`; delta by `changed_at` of the entries, removes when a machine leaves the site. Reads use the
  existing indexes of `fieldops.shift_entries` (current version per root).
- **Tablet:** Dexie schema v3 adds `meterStates` and `drafts`; `applyChanges` stores the collection; an upgrade test
  from v2 keeps the outbox and blobs (TC-P2-SYNC-007 storage side).
- **Shift resolution:** `shifts.ts` `shiftAt(patterns, timeZone, instant)` → `{date, code, startsAt, endsAt}` with
  `Intl.DateTimeFormat` for the site clock; `tests/vectors/shift-resolution.json` read by `shifts.test.ts` and an
  Organization test class.
- **Reference value:** `meterReference(db, meterId)` = the newest of the pulled `lastEnd` and the tablet's own
  pending end commands; open segment likewise.
- **Tests:** vectors both sides; `FieldOpsSyncTests` (Testcontainers: rows, delta, removes, tenant isolation, other
  site not sent); `@karry/offline` v2 → v3 upgrade; TC-P2-FO-001 logic part (night shift across midnight
  preselected).

### Slice 4: sign and enqueue

- `signShiftEntry(db, session, input)` in the field app: validates with `startRecordProblem` / `endRecordProblem`
  first (never signs a record the server would refuse), builds evidence and envelope (`@karry/crypto`
  `payloadHash`, `handwrittenHashes`, `signEnvelope`), position (decision 7), enqueues with `enqueue`.
- **Tests:** unit (payload shape, envelope binding: recordType, recordId, recordVersion, payloadHash; evidence list
  = photo + strokes + PNG; no `geo` when refused); a **server round trip** in `Karry.Host.IntegrationTests`: the
  vector of a command made by the TypeScript code (fixture written by a vitest test into `tests/vectors/`) is
  accepted by `/sync/batches` and verified by the envelope verification endpoint, so the two languages agree on the
  whole command, not only on the record.

### Slice 5: start-shift flow

- Home action "Start a shift" (replaces the "coming soon" meter action). Steps on one scrolling screen, large
  targets: machine (`MachineFinder`: QR or site list) → shift (preselected, previous/next only) → previous end shown
  (or "no previous value on this tablet") → meter photo (`PhotoCapture`, lazy) → start value (numeric keypad,
  `inputmode="decimal"`, one decimal) → fuel slider 0–100 with ¼ marks → remarks (optional; the system keyboard's
  voice input) → summary → `SignaturePad` (lazy, "I confirm the values above") → outbox → home with "Saved, will be
  sent" in the sync centre.
- Blocks with the explanation: value below the previous end (TC-P2-FO-003); an open segment of this operator on any
  machine (US-P2-FO-05 AC2); an open segment of another operator on this machine offers "Continue after <name>"
  only once that segment is ended. Unusual jump → reason required (decision 5).
- The unlocked person's name on every step (T-01); auto-lock keeps the draft (decision 4).
- **Tests:** component tests per step and the whole flow with fakes (camera, position, pad); TC-P2-FO-001
  (offline QR start → draft saved → signed command in the outbox, night shift preselected), TC-P2-FO-003, axe on
  each step, five languages render (pseudo-locale length check).

### Slice 6: "My active shift", end and handover

- Home shows "My active shift" when the unlocked operator has an open segment (pulled or own): machine, start
  value, started at, running time. End flow: end photo → end value → Δ live with `endFlags` (negative or oversized
  blocks with the explanation; km meters: negative only) → fuel → stoppages (reason list, minutes) → summary
  start/end/Δ (US-P2-FO-04 AC3) → sign → outbox. The record version is the open segment's next version.
- Handover: after an end, the next operator's start on that machine sets `previousRootId` and shows the end value
  as the reference.
- **Tests:** end flow with fakes; the blocks; handover start carries `previousRootId`; an end on a segment the
  tablet only knows from the pull.

### Slice 7: "My history"

- The operator's entries of the last 14 days from the outbox and the pulled `submissions`: Draft (local), Queued
  (in the outbox), Submitted (accepted / conflict, with the flags), Rejected (code → message from the catalogs).
  Thumbnails from the blob store (kept after purge). Re-opening a **sync** rejection starts a new draft from its
  values; controller rejections come with P2.8.
- **Tests:** list states from a seeded outbox and submissions; 14-day cut-off; no other operator's entries.

### Slice 8: browser E2E (Playwright, `src/frontend/e2e`)

- Chromium with `--use-fake-device-for-media-stream --use-fake-ui-for-media-stream` (a fake camera) and
  geolocation granted; the local stack with SeaweedFS and OpenBao.
- **Cases:** offline (context `setOffline(true)`) start → end → sign → online → the portal API shows one signed
  entry with two photos, envelope `verified`; TC-P2-SYNC-002 (context closed mid-upload → reopened → resumes, no
  duplicate); TC-P2-SYNC-007 (service worker update with a non-empty outbox → intact, upload continues);
  TC-P2-SYNC-011 (a photo not purged while its entry is not confirmed); TC-P2-SYNC-014 (two tabs → one upload, no
  sequence reuse, the `PUT` passes the bucket CORS rule); the P2.3 E2E (verified also after `karry-server` key
  rotation); "done when": 20 entries with photos queued offline arrive once, verified.
- Runs in the `local-stack` CI job (the stack is already up there); budget ≤ 10 min.

### Slice 9: close-out

- Bundle budget checked with the lazy chunks named in the CI summary; translation review rows for every new key
  (ar, emk drafts; nqo generated); security review in ADR-0034 (T-01 name on every screen and auto-lock inside the
  flow, drafts per operator; T-17 drafts and thumbnails on a lost tablet, cleared on revocation); usability
  protocol (3–5 operators or a proxy group, median start ≤ 60 s) written as an owner task if no operator is
  available; demo steps 1–2 on the local stack (without the checklist); tracker P2.5 ✅; hand-off.

## 4. Risks

| Risk | Mitigation |
|---|---|
| A low-end tablet's camera gives 4K frames and the encode takes seconds | `getUserMedia` asks for 1920×1080 ideal; encode measured in slice 5 on the mid-range phone; downscale before WebP if > 1 s |
| WebP encode missing (old Safari) | JPEG fallback already in `encodeFrame` (slice 2) |
| Intl time zone data differs between the tablet and .NET | shared `shift-resolution.json` includes a DST zone and a version switch day |
| The pulled open segment is stale (ended on another tablet, not yet synced) | the end is still signed; the server flags `OVERLAP`/continuity; the screen says "as of the last refresh <time>" |
| E2E flakiness with the fake camera and service worker | one worker, retries 0 locally / 1 in CI, traces kept on failure |

## 5. Owner inputs

- Stoppage reason codes (US-P2-FO-04 AC1): fixed list `breakdown, weather, no_material, no_operator, other` until
  confirmed (ADR-0034 §8).
- Unusual-jump threshold default (24 h proposed).
- Operators (or a proxy group) and a mid-range phone for the usability test (slice 9).
