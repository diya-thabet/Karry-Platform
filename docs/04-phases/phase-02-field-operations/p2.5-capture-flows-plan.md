# P2.5 field capture flows: slice plan

> [Docs index](../../README.md) › [04-phases](../README.md) › [Phase 2 plan](plan.md) · [Sub-phases](sub-phases.md#p25--field-capture-flows-tablet) · [Tracker](tracker.md)

**In plain words:** the operator starts and ends a shift on the tablet: finds the machine, photographs the meter,
types the value, sets the fuel level, signs, and the entry waits in the outbox until there is network. This file
splits [P2.5](sub-phases.md#p25--field-capture-flows-tablet) into small PRs, says what each one builds and how it is
tested, and records the decisions taken while planning. The server side already exists: commands
`fieldops.shift_entry.start.v1` / `.end.v1`, flags and the read API ([ADR-0034](../../adr/0034-shift-entries.md)),
envelopes ([ADR-0033](../../adr/0033-signature-envelopes-and-server-keys.md)), evidence blobs and the outbox
([ADR-0032](../../adr/0032-evidence-blobs.md)).

## 1. Scope

| Story | ACs in P2.5 | Left for later |
|---|---|---|
| US-P2-FO-01 Start a shift | AC1 (QR or list, shift preselected), AC2 (in-app photo, previous end shown), AC3 (fuel ¼ marks, remarks with the system's voice keyboard), AC4 on the tablet (below the previous end blocked; unusual jump needs a reason), AC5 capture (position in the envelope), AC6 (offline draft), AC7 (usability protocol) | AC4 meter events and AC5 geofence flag: P2.7 rules |
| US-P2-FO-04 End a shift | AC1 (from "My active shift": photo, value, fuel, stoppages), AC2 on the tablet (negative or oversized Δ blocked with the explanation), AC3 (summary start/end/Δ before signing) | the meter-event exception: P2.7 |
| US-P2-FO-05 Handover | AC1 screen (continue after the previous segment: `previousRootId`), AC2 on the tablet (no second active segment for the same operator) | |
| US-P2-FO-06 My history | AC1 for what the tablet knows (Draft, Queued, Submitted, Rejected with reason) | Approved / Corrected and AC2 re-open of a controller rejection: P2.8 (status pull of reviews) |
| From P2.2 / P2.3 | browser E2E TC-P2-SYNC-002/007/011/014; an entry signed in the browser verified end to end, also after a key rotation | |

Not in P2.5: the pre-start checklist (P2.6; demo step 1 runs without it until then), fuel issues and production
(later sub-phases), Web Push (P2.8).

## 2. Decisions taken while planning

1. **The tablet blocks what the server would only flag.** ADR-0034 stores every signed fact and flags it; US-P2-FO-01
   AC4 and US-P2-FO-04 AC2 ask the tablet to stop the operator *before* signing. Both hold: the tablet refuses to
   sign a start below the meter's previous end, a negative Δ or a Δ beyond the real length + 0.5 h, with the reason
   on screen; the server still flags whatever arrives (another tablet, an old app). The rules are the shared ones of
   slice 1 (`shiftRules.ts`), so the tablet never blocks what the server accepts unflagged.
2. **The previous end comes from a new FieldOps sync collection, `meterStates`.** The meters the tablet pulls (Assets)
   carry no value, and `assets.meters.last_value` is not written by shift entries. FieldOps owns the answer: per
   meter of the site, the last segment's end (value, time) and the open segment if any (entry id, operator, start
   value, start time, shift). The tablet's own unsent commands win over the pulled state (they are newer by
   construction), so the reference is right offline too.
3. **The shift is computed on the tablet with the server's rules, proven by a second shared vector file**
   (`tests/vectors/shift-resolution.json`): pattern versions by effective date, night shifts across midnight,
   the site's time zone (with a DST zone in the vectors even though Tunisia has none), equal times = 24 h. The server
   side runs the same file through the Organization domain. The operator can change the preselected shift only to
   the previous or the next instance (late start, early handover).
4. **Drafts live in a new Dexie table (`drafts`, schema v5, slice 5)**, one per operator and form, written at every step;
   nothing of a draft is signed or sent. After an auto-lock, the draft reopens only for the same operator; another
   operator sees "a draft of <name> is open on this machine" and cannot open it (T-01). Drafts older than 24 h are
   offered for discard.
5. **The unusual-jump reason goes into `remarks`.** The record has no reason member and a new member would mean
   a new record version; the reason is prefixed in the remarks (`remarks` becomes required for that start). The
   threshold is a constant (24 h) until a company setting exists (owner input, §5).
6. **One command per signature, built by one function.** `signShiftEntry` builds the record, takes the evidence
   (meter photo, signature strokes JSON, signature PNG), computes `payloadHash`, builds the envelope (signer =
   unlocked operator, role `operator`, `context.deviceTime`, `appVersion`, `geo` when the browser gave a position
   within 10 s), signs it, and enqueues `{record, envelope, deviceSignature, captures}` with the evidence. The capture
   records ride in the signed command payload (`captures`, ADR-0032 §5); the server keeps the command as received.
7. **Position:** asked once per form with `getCurrentPosition` (high accuracy, 10 s timeout, a cached position up to
   2 min old accepted); refused or timed out → no `geo`, never a blocker. Rounded to 6 decimals as stored.
8. **Lazy chunks:** the camera (`PhotoCapture`) and the signature pad are loaded by the flows with `React.lazy` and
   preloaded when the flow opens, so the first photo does not wait on the network; the precache keeps them offline.
   The initial bundle stays ≤ 250 KB gzip (CI `bundle_budget.py`).

### Slice 3: reference data for capture

- **Server (FieldOps, as built in 3a):** `MeterStatesSync : ISyncSource`, collection `meterStates`, one row per meter
  with an entry on the tablet's site: `{id (meter), lastEnd: {entryId, value, at} | null, open: {entryId, version,
  operatorId, startedAt, startValue, shiftDate, shiftCode} | null}`. A meter's last segment is its latest started
  current version (as the start handler reads it, ADR-0034 §5): open → `open`; the latest started *closed* one gives
  `lastEnd`. Two `DISTINCT ON (meter_id)` queries return entry IDs only (EF cannot map raw SQL onto an entity with
  optional complex properties), then the versions load through LINQ. Delta: the meters with a version received
  (`received_at`) since the cursor; one with no entry on this site any more is a remove. An entry's site is the site
  of the tablet that sent it.
- **Tablet (as built in 3a):** Dexie schema v3 adds `meterStates` (`drafts` moves to slice 5, which writes it);
  `applyChanges` stores it like any collection; the upgrade test opens a v2 database with its outbox and blobs.
  `apps/field/src/meterState.ts` merges the pulled row with the tablet's own shift commands (not refused ones): an
  own end closes the running segment, an own start after the last end becomes the running segment, a segment that
  started before the last end is not running (never ended).- **Found while building 3a, for 3b:** the server's `ShiftCalendar.Resolve` skips the site's **non-working days**, and
  the tablet's pull does not carry them (Organization sends `sites` and `shiftPatterns` only). 3b added them to the pull
  (replace-whole collection of the coming days); without them the tablet would preselect a shift the server leaves empty.
  The port must also keep NodaTime's DST rules (a start in a spring-forward gap moves forward by the gap; one in a
  fall-back overlap takes the earlier offset) and the 60-minute early start (ADR-0034 §2).
- **Shift resolution (as built in 3b):** `apps/field/src/shifts.ts` `shiftAt(timeZone, versions, nonWorkingDays,
  instant)` ports `ShiftCalendar.Resolve`: the newest version effective on each local date, nothing on a non-working
  day, the shift running at the instant else the one starting within 60 minutes. Local times go through `Intl`
  (`instantOf`): of the offsets 12 h before and after, the valid ones give the instant (the earlier one in a fall-back
  overlap); none valid means a spring-forward gap, read with the offset before the change (NodaTime's "forward
  shifted"). `tests/vectors/shift-resolution.json` (22 hand-written cases: three-eights, early start, gaps, Saturday,
  non-working days, a pattern version switch, 24-hour shifts, Europe/Paris clock changes both ways, a zone west of
  UTC) is read by `ShiftCalendarVectorsTests` (server, NodaTime) and `shifts.test.ts` (tablet). Organization's sync
  adds `nonWorkingDays` (replace-whole, the site's days from two days ago); Dexie v4 stores them.
- **Tests:** 3a: `ShiftEntryHandlersTests` (Testcontainers: snapshot with last end and running segment of the
  site only, other company not seen; a never-ended segment not running; delta of changed meters only; remove when a
  meter's new entries are on another site), `@karry/offline` v2 → v3 upgrade and meter state rows,
  `meterState.test.ts`. 3b: vectors both sides (TC-P2-FO-001 logic part: night shift across midnight), `SyncChangesTests` (non-working days of the site from two days ago, replace-whole), offline v2 → v4 upgrade.

### Slice 4: sign and enqueue

- **As built:** `apps/field/src/signShiftEntry.ts`: `signStart` / `signEnd` build the record and check it with
  `startRecordProblem` / `endRecordProblem` first (a record the server would refuse throws `RecordRefused` and nothing
  is stored), then the envelope: `payloadHash` of the record, `evidence` = the meter photo's hash, `handwritten` = the
  strokes and PNG hashes, signer = the unlocked operator (role `operator`) on this device, `context.deviceTime`,
  `appVersion` and `geo` when `browserPosition` answers within 10 s (rounded to 6 decimals, accuracy rounded up to
  the metre, as stored). It is signed with the device key and enqueued as `{record, envelope, deviceSignature,
  captures}` with three blobs: the photo (with its thumbnail), the strokes JSON and the PNG.
- **Tests:** `signShiftEntry.test.ts` (the envelope verifies with the device key and binds record, photo and
  handwriting; a changed value no longer matches; an end as the next version; no `geo` when refused; an invalid record
  is never signed nor stored; positions rounded).
- **Decision (planning said "server round trip" here):** the record shape, RFC 8785 and the envelope format are each
  already proven identical on both sides by shared vectors (`shift-entry-rules.json`, `rfc8785.json`,
  `signature-envelope.json`), and the payload's members are checked by the handlers (**this was wrong at first**: `SignedRecord.Read` accepted exactly `record`, `envelope`, `deviceSignature`, so every real command, which also carries `evidence` and `captures`, was refused `fieldops.entry_invalid`; found by the 8a browser E2E, the server now accepts exactly those five). The whole command,
  signed in a real browser and verified by the server, is the slice 8 E2E ("an entry signed in the Playwright
  browser is verified end to end"); a hand-made cross-language fixture here would need a second enrolment path in the
  host tests for no additional proof.
### Slice 5: start-shift flow

- Home action "Start a shift" (replaces the "coming soon" meter action). Steps on one scrolling screen, large
  targets: machine (`MachineFinder`: QR or site list) → shift (preselected, previous/next only) → previous end shown
  (or "no previous value on this tablet") → meter photo (`PhotoCapture`, lazy) → start value (numeric keypad,
  `inputmode="decimal"`, one decimal) → fuel slider 0–100 with ¼ marks → remarks (optional; the system keyboard's
  voice input) → summary → `SignaturePad` (lazy, "I confirm the values above") → outbox → home with "Saved, will be
  sent" in the sync centre.
- Blocks with the explanation: value below the previous end (TC-P2-FO-003); an open segment of this operator on any
  machine (US-P2-FO-05 AC2); an open segment of another operator on this machine offers "Continue after <name>"
  only once that segment is ended. Unusual jump → reason required (decision 5).
- The unlocked person's name on every step (T-01); auto-lock keeps the draft (decision 4).
- **Tests:** component tests per step and the whole flow with fakes (camera, position, pad); TC-P2-FO-001
  (offline QR start → draft saved → signed command in the outbox, night shift preselected), TC-P2-FO-003, axe on
  each step, five languages render (pseudo-locale length check).

- **As built in 5a:** home button "Start my shift" (the "Hour meter, coming soon" action is gone) opens
  `StartShift.tsx`: `MachineFinder` with a "Use this machine" button (QR or the site's list), then on one screen the
  machine, the shift of now (`shiftAt`), the previous end (`readMeterState`), the meter photo (`PhotoCapture`, lazy),
  the start value (`inputmode="decimal"`), the fuel slider (0–100, ¼ marks), remarks, "Check and sign", the summary
  and the pad (`SignStep`, lazy), then `signStart`. The rules are `startRules.ts` (`assessStart`, `entryMeter`,
  `hasRunningSegment`). `@karry/ui` is now marked `"sideEffects": ["*.css"]` so the pad really leaves the initial
  bundle: initial JS 213.7 KB gzip (budget 250), pad chunk 2.0 KB, camera chunk 1.1 KB.
- **Decision (planning said "shift preselected, previous/next selectable"):** the record has no shift member; the
  server resolves the shift from `startedAt` (ADR-0034 §2). The screen shows the shift the server will store, and a
  selector would let the operator pick one the record cannot carry. The shift is shown, not chosen.
- **Tests (5a):** `startRules.test.ts` (TC-P2-FO-003 below the previous end, value format, 24 h jump needs a reason,
  km meters exempt, machine in use, a second running shift, meter choice, running segment found in pulled states and
  own commands), `StartShift.test.tsx` (TC-P2-FO-001: offline, night shift across midnight shown, signed start in the
  outbox; TC-P2-FO-003 on screen; reason required; machine in use by a named operator), `App.test.tsx` (home offers
  the start).
- **As built in 5b:** Dexie v5 `drafts` (`DraftRecord`: `{operatorId}:{form}`, `values`, `updatedAt`); `drafts.ts`
  (`readDraft` drops a draft older than 24 h, `saveDraft`, `discardDraft`). `StartShift` reads the operator's draft
  once when it opens (machine, value, fuel, remarks and the photo bytes; never the signature) and says so on screen,
  saves at every change, and drops it when signed or when the operator leaves with the back button; an auto-lock only
  unmounts the form, so the draft stays. Draft writes are chained and stop once the form closes: a save still on its
  way had brought back a dropped draft (found by the test), and an opened, untouched form is not saved (it had made
  an empty draft per operator who only looked).
- **Tests (5b):** `drafts.test.ts` (one per operator and form, another operator never sees it, 24 h), `StartShift.test.tsx`
  (left by a lock and found again by the same operator only, dropped when left on purpose, none after signing),
  offline v2 → v5 upgrade.
### Slice 6: "My active shift", end and handover

- Home shows "My active shift" when the unlocked operator has an open segment (pulled or own): machine, start
  value, started at, running time. End flow: end photo → end value → Δ live with `endFlags` (negative or oversized
  blocks with the explanation; km meters: negative only) → fuel → stoppages (reason list, minutes) → summary
  start/end/Δ (US-P2-FO-04 AC3) → sign → outbox. The record version is the open segment's next version.
- Handover: after an end, the next operator's start on that machine sets `previousRootId` and shows the end value
  as the reference.
- **Tests:** end flow with fakes; the blocks; handover start carries `previousRootId`; an end on a segment the
  tablet only knows from the pull.

- **As built:** `endRules.ts` (`findActiveShift`: the operator's running segment from the pulled states and the tablet's
  own commands; `assessEnd`: the shared `endFlags` turned into reasons: `below`, `tooLong`, `beforeStart`, `value`).
  Home shows "My active shift" (machine, start value and time) with "End my shift" instead of "Start my shift" while
  one runs. `EndShift.tsx`: end photo, end value with Δ shown as typed, fuel, stoppages (reason buttons for gloves,
  minutes 1–1440, up to 20), remarks, summary start/end/Δ, pad, `signEnd` with the next version. **Handover:** a start
  whose machine's last end falls inside the current shift names it (`previousRootId`), so the server checks
  continuity against that end (US-P2-FO-05 AC1).
- **Tests:** `endRules.test.ts` (8.5 h accepted, 8.6 h refused on an 8 h segment, backwards, end not after start, km
  without time limit, active shift found only for its operator), `EndShift.test.tsx` (Δ shown, a stoppage, signed end
  as version 2 with the stoppage, the shift no longer active; backwards and too long refused), `StartShift.test.tsx`
  (handover names the previous segment). `PhotoCapture.test.tsx` now waits for the camera release (it raced under
  load).
### Slice 7: "My history"

- The operator's entries of the last 14 days from the outbox and the pulled `submissions`: Draft (local), Queued
  (in the outbox), Submitted (accepted / conflict, with the flags), Rejected (code → message from the catalogs).
  Thumbnails from the blob store (kept after purge). Re-opening a **sync** rejection starts a new draft from its
  values; controller rejections come with P2.8.
- **Tests:** list states from a seeded outbox and submissions; 14-day cut-off; no other operator's entries.

- **As built:** `historyRows.ts` (one row per entry from the operator's own shift commands of the last 14 days, newest
  first: start, end, latest photo, flags, and the worst state: refused, then to send, then received), `History.tsx`
  (home button "My history": machine, status chip, start and end with time, Δ, the flags in words, the reason of a
  refusal, the photo's kept thumbnail, a start left unsigned with "Continue"; a refused start "Start again with
  these values" writes the start form's draft from them, the photo to take again). `refusals.ts` holds the refusal
  explanations the sync centre and the history share.
- **Not here:** rows for entries signed on another tablet (the server's `submissions` only tell this tablet about its
  own commands) and "approved / corrected" (P2.8 status pull).
- **Tests:** `historyRows.test.ts` (rows and order, refusal over everything with the start's values, operator and 14
  days), `History.test.tsx` (statuses, Δ, flag text, refusal reason; start again writes the draft; continue a draft).

## 4. Risks

| Risk | Mitigation |
|---|---|
| A low-end tablet's camera gives 4K frames and the encode takes seconds | `getUserMedia` asks for 1920×1080 ideal; encode measured in slice 5 on the mid-range phone; downscale before WebP if > 1 s |
| WebP encode missing (old Safari) | JPEG fallback already in `encodeFrame` (slice 2) |
| Intl time zone data differs between the tablet and .NET | shared `shift-resolution.json` includes a DST zone and a version switch day |
| The pulled open segment is stale (ended on another tablet, not yet synced) | the end is still signed; the server flags `OVERLAP`/continuity; the screen says "as of the last refresh <time>" |
| E2E flakiness with the fake camera and service worker | one worker, retries 0 locally / 1 in CI, traces kept on failure |
