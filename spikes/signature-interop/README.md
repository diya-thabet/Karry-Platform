# Spike WP-P0-11 (part 2) — Browser signature verified by .NET

**Question.** Can the .NET backend verify a signature produced by Chromium WebCrypto (ECDSA P-256 / SHA-256) over an RFC 8785 canonical payload?

**Status:** ✅ Answered (2026-10-21, .NET 10.0.402).

The fixture [`fixtures/browser-vector.json`](fixtures/browser-vector.json) is generated by the PWA spike in real Chromium (`UPDATE_SIGNATURE_VECTOR=1 pnpm exec playwright test -g TC-P0-KEY-003`).

| Test | Verifies | Result |
|---|---|---|
| TC-P0-SIG-001 | Browser signature verifies with `ECDsa.VerifyData(..., IeeeP1363FixedFieldConcatenation)` | ✅ |
| TC-P0-SIG-002 | SHA-256 of the canonical payload matches the browser's `payloadHash` | ✅ |
| TC-P0-SIG-003 | Modified payload is rejected | ✅ |
| TC-P0-SIG-004 | Assuming DER encoding would wrongly reject a valid signature (interop trap documented) | ✅ |

**Decisions for Phase 1**
- Server verification uses `DSASignatureFormat.IeeeP1363FixedFieldConcatenation` (WebCrypto emits 64-byte r‖s, not DER).
- The server must canonicalize exactly as the client does. Phase 1 adds a shared **RFC 8785 test-vector suite** run by both the TypeScript and .NET test projects (numbers, Unicode and key ordering are the risky parts; this spike only covers strings, integers and null).
